# 工作流与冲突处理

## 从零设计或改进

先找到主要用户任务、核心数据、使用频率和页面上下文。沿用项目的品牌、密度、组件和 Token；没有这些约束时才建立最小方案。重要操作、当前状态和恢复路径要清楚，装饰不得压过任务。

页面结构先于视觉细节。按当前问题读取 `better-layout`、`better-writing`、`better-typography`、`better-colors`，涉及交互时读取 `better-accessibility`，需要表面或动画处理时读取 `better-ui`。完整审查才由 `better-interface` 加载全部领域。

没有明确的审美方向时，可以解释一个可行方向及它的取舍；只有用户要求多个候选时才进入 `variant`。已有设计足以推进时不要为无关偏好停下。

## 从参考网页迁移

用户要求分析时，使用 `explain-interface` 区分实测、推导和推测；截图只能支撑重建假设。看不到源码或运行状态时标记限制，不把近似值写成实测事实。

用户要求借鉴或实现时，在解释后把可迁移机制映射到目标项目：信息层级、分组、文字比例、状态反馈、动效节奏和渐变图层。依赖具体宽度、品牌、字体或图片的值需要重新验证，不能当作通用设计规范。

## 忠实还原设计稿

按 `build-design` 读取设计来源、映射 Token/组件并逐帧比较。源稿缺失的状态采用既有组件默认值并列出缺口；用户要求补全时才设计这些状态。

显著 Token 舍入、缺少组件或源稿违反可访问性要求时，报告具体差异和可行方案。用户已经给出的相关取舍直接执行，不重新索取同一批准。

## 手势与共享布局

原设计规范第 11–12 章补充上游领域：拖拽应有轴、边界、Commit Threshold 和确定落点；需要可预测 Snap 时限制动量，并提供非手势入口。阈值随组件尺度和任务测试，不沿用文章演示中的固定像素。

Shared Layout 用于同一对象跨状态的连续关系。保持分组内标识唯一，区分移动实体与随状态进入/退出的内容。结合 `better-ui` 的高频操作与 Reduced Motion 规则决定是否需要动画，不把 Shared Layout 作为默认的 Tab 装饰。

## 冲突与数值

数值先来自明确设计稿或项目设计系统。原 SP 的字号、间距、行高和颜色数量建议是起点；中文、英文和密集工具不必套用同一行长或字号。旧 SP 与最新上游细则不同，由最新领域规则补充，并保留项目明确且一致的风格选择。

遇到实际阻碍任务、隐藏操作或破坏可访问性的情况，引用代码/运行证据提出修复。与用户明确需求冲突时说明具体取舍；不要把个人风格差异当作 Bug，也不要重写上游文件来掩盖冲突。

## 性能、本地化与状态

原 SP 第 14–15 章补充资源加载、渲染成本及 Locale-aware 格式。验证工具、产品支持范围和性能目标由项目决定；不为了遵循规范引入新库、后台进程或全站改造。

新设计考虑真实可达的加载、空、错误、权限与完成状态。审查、`state-machine` 和 `break` 以实际实现和数据边界为证据，不通过制造生产代码不可达的分支扩大任务。

## 完成标准

实现交付前检查真实内容、窄容器、长文本、Focus、触控及快速重复操作；动画检查可打断性和 Reduced Motion。按改变涉及的领域运行项目现有检查，注明验证范围。没有渲染过的页面不宣称视觉还原，无真实后端的演示注明数据来源。
